# SQL Materializer redesign

Transaction Service commits the basket line, running total, and one raw event in one InnoDB transaction before acknowledging the Scan. It locks the target checkout row, but never the global sequence. `event_id` is an immutable unique `AUTO_INCREMENT` identity, not an ordering cursor. It may have gaps or commit out of order. `position` starts NULL.

The Materializer locks the singleton `scan_sequence` checkpoint, selects a bounded batch of **all committed rows whose `position IS NULL`** ordered by event ID, assigns consecutive positions starting at `last_position+1`, updates that checkpoint, then commits once. The ordering rule is event ID among pending rows visible to each batch, not physical commit order. It never uses an event-ID high water mark. A lower ID that commits late remains discoverable. The singleton serializes Materializer batches only; Scan commits do not acquire it. A unique non-NULL `position` constraint and the event primary key enforce identity and position uniqueness. Only Materializer code updates positions.

A crash before the batch commit rolls back positions and checkpoint. A crash after commit leaves both durable; retry sees no pending rows from that batch. A second Materializer waits for the checkpoint lock and then discovers the remaining pending set. Rollback of a Scan leaves no event, line, or total; event-ID gaps do not imply position gaps. Previously assigned positions are immutable.

Analytics reads the committed, contiguous positioned prefix in ascending position, checks adjacency, and uses the existing Window, Ranking, and Persistence queues. The first window remains positions 1–1,000; the hop remains 500. Counts rank descending, ties by SKU ascending, capped at ten. Window results and their checkpoint still commit atomically. On restart, Analytics prewarms from its last committed window and replays; the Materializer resumes from the NULL-position predicate. Unpositioned committed rows are backlog, not permanent gaps.

Schema constraints: `accepted_scan.event_id` primary key, nullable unique `position`, and an index supporting pending discovery; `scan_sequence.last_position` equals the highest committed position. The likely costs are checkout-row contention within one basket, Scan SQL round trips and fsynced commits, pending-index scans and row updates, and the sequence checkpoint lock once per batch. Batch size trades lock duration against lag. Benchmarks must measure Scan throughput and p95/p99, Materializer events/sec, pending count/age, and InnoDB lock waits without changing MySQL durability or the load client.
