# Data Model: Self-Checkout Microservices

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Decisions**: [research.md](research.md) (revised 2026-10-20 for the memory-first design, R18–R22)

Each service owns one MySQL schema and reaches it only through its own credentials (R3). No foreign key, view, routine, or query crosses schemas. Values that refer to another service's data, such as transaction IDs or SKUs, are plain values. Durable tables hold only what business state, recovery, idempotency, reliable delivery, and externally visible guarantees require (R18). Everything else lives in the in-memory projections listed at the end, which are rebuilt from these tables.

| Schema | Owner | Database user | Session settings (R20) |
|---|---|---|---|
| `cs6510_transaction` | Transaction Service | `cs6510_transaction_svc` | Manual commit, READ COMMITTED |
| `cs6510_inventory` | Inventory Service | `cs6510_inventory_svc` | Manual commit, READ COMMITTED |
| `cs6510_analytics` | Analytics Service | `cs6510_analytics_svc` | Manual commit, READ COMMITTED |

Types are design-level MySQL 8 types. Exact DDL lives in `db/<service>/schema.sql` at implementation. All timestamps are UTC with millisecond precision. Values written by Start, T3, and Scan are generated by the owning service and passed in, so no statement has to read them back.

## Transaction schema (`cs6510_transaction`)

### `transaction`

| Column | Type | Rules |
|---|---|---|
| `transaction_id` | VARCHAR(40), PK | UUID created by Start |
| `station_id` | VARCHAR(40), not null | 1–40 characters (existing validation) |
| `status` | ENUM(`OPEN`,`COMPLETED`,`CANCELLED`), default `OPEN` | No public operation sets `CANCELLED` |
| `item_count` | INT, not null, default 0, ≥ 0 | Number of accepted scans. Doubles as the guarded-write version: every Scan's guarded UPDATE expects the cached value and writes value + 1 (R19). |
| `total_amount` | DECIMAL(12,2), not null, default 0 | Sum of captured unit prices over accepted scans |
| `attempt_count` | INT, not null, default 0 | Number of checkout attempts created |
| `active_attempt_number` | INT, null | Non-null exactly while a PENDING attempt exists, freezing the basket (FR-035). Indexed for the recovery worker. |
| `started_at` | TIMESTAMP(3) | Supplied by Start |
| `completed_at` | TIMESTAMP(3), null | Supplied by T3. Non-null exactly when `status = COMPLETED`. |

Checks: `status = COMPLETED` if and only if `completed_at IS NOT NULL`, and `status = COMPLETED` implies `active_attempt_number IS NULL`.

Writes are always guarded conditional UPDATEs. The `WHERE` clause repeats the expected `status`, `active_attempt_number`, and `item_count`, as applicable. Zero affected rows means the request must re-evaluate from the database (R19).

### `accepted_scan` (scan log, basket record, and outbox; R10)

| Column | Type | Rules |
|---|---|---|
| `scan_id` | BIGINT, auto-increment, PK | Relay selection order only |
| `transaction_id` | VARCHAR(40), FK → `transaction` | First part of the event identity |
| `scan_sequence` | INT, ≥ 1 | Equals the transaction's `item_count` after this scan; second part of the event identity |
| `sku` | VARCHAR(20) | Present in the product replica when accepted |
| `product_name` | VARCHAR(100) | Captured when the SKU was first accepted into this transaction |
| `unit_price` | DECIMAL(10,2), ≥ 0 | The line's captured price. Identical for every row of the same `(transaction_id, sku)` (FR-019). |
| `accepted_at` | TIMESTAMP(3) | Supplied by Scan |
| `delivered_at` | TIMESTAMP(3), null | Set only after Analytics acknowledges durable receipt |

Unique key: `(transaction_id, scan_sequence)`. This also serves basket reconstruction, by reading the rows of one transaction. Index: `(delivered_at, scan_id)` for the relay.

Basket lines are derived from these rows rather than stored separately: one line per SKU, with quantity equal to the row count, plus the captured price and name. Rows are written only by the Scan transaction and are retained after delivery.

### `product_replica` and `product_replica_meta`

| Table | Columns | Rules |
|---|---|---|
| `product_replica` | `sku` (PK), `name`, `price` DECIMAL(10,2), `catalog_version` CHAR(36) | Full copy of Inventory's catalog, replaced in one local transaction when the version changes (R4) |
| `product_replica_meta` | `meta_key` (PK = 1), `catalog_version` (null until the first load), `product_count`, `refreshed_at` | A null version means no usable product information, so Scan returns 500 (FR-023) |

### `checkout_attempt`

| Column | Type | Rules |
|---|---|---|
| `transaction_id` | VARCHAR(40), FK → `transaction` | First part of the attempt identifier |
| `attempt_number` | INT, ≥ 1 | Second part of the attempt identifier; equals `transaction.attempt_count` at creation |
| `state` | ENUM(`PENDING`,`COMPLETED`,`REJECTED`) | See the state machine |
| `rejection_reason` | ENUM(`INSUFFICIENT_STOCK`,`INVALID_REQUEST`,`STOCK_RESTORED`), null | Non-null exactly when `state = REJECTED` |
| `rejected_sku` | VARCHAR(20), null | The SKU named in `409 INSUFFICIENT_STOCK` |
| `lines` | TEXT, not null | Immutable canonical snapshot: a JSON array of `{sku, quantity}` sorted by SKU, with no whitespace. This is the exact payload sent on every replay. |
| `item_count`, `total_amount` | Snapshot | Used for the receipt |
| `client_outcome` | ENUM(`NONE`,`SUCCESS`,`REJECTED`,`PENDING_ERROR`), default `NONE` | Written inside the T3 or reopen UPDATE; `PENDING_ERROR` is committed before a pending 500. A request whose own attempt was settled by another actor writes its outcome with a guarded UPDATE (`client_outcome = 'NONE'`) before answering (R9). |
| `created_at`, `settled_at` | TIMESTAMP(3); `settled_at` null while PENDING | Supplied by the service |
| `retry_count`, `next_retry_at`, `last_error` | Recovery bookkeeping | Backoff and the last uncertain status (R6). T1 sets `next_retry_at` to `created_at` plus the response budget, so recovery scans leave a live request's attempt alone. A budget-expiry handover sets it to now. Recovery sets it with backoff (R7). |

Keys:
- Primary key `(transaction_id, attempt_number)`.
- Index `(state, next_retry_at)`.
- Defense-in-depth unique generated columns: `pending_transaction_id = IF(state='PENDING', transaction_id, NULL)` and `completed_transaction_id = IF(state='COMPLETED', transaction_id, NULL)`.

## Inventory schema (`cs6510_inventory`)

### `catalog_item`, `inventory`, `catalog_meta`

| Table | Columns | Rules |
|---|---|---|
| `catalog_item` | `sku` (PK), `name`, `price` DECIMAL(10,2) ≥ 0 | Deterministic seed of 2,000 products (FR-052) |
| `inventory` | `sku` (PK, FK → `catalog_item`), `stock_quantity` INT CHECK ≥ 0, `low_stock_threshold` INT ≥ 0 | Seeded with 10,000 units and threshold 50. Changed only by checkout operations. Never cached. |
| `catalog_meta` | `meta_key` (PK = 1), `catalog_version` CHAR(36), `product_count`, `seeded_at` | A new UUID at every reset or reseed (R4) |

### `checkout_operation`

| Column | Type | Rules |
|---|---|---|
| `transaction_id`, `attempt_number` | VARCHAR(40), INT; PK together | The attempt identifier. Plain values with no reference to Transaction's schema. |
| `state` | ENUM(`APPLIED`,`REJECTED`,`RESTORED`,`BLOCKED`) | See the state machine |
| `rejection_reason` | ENUM(`INSUFFICIENT_STOCK`,`INVALID_REQUEST`), null | Non-null exactly when `state = REJECTED` |
| `rejected_sku` | VARCHAR(20), null | First unknown or short SKU, in SKU order |
| `lines` | TEXT, null | The canonical payload, as in `checkout_attempt.lines`. A replay must match it exactly, or it gets `FAILED_PRECONDITION`. These are the exact units restored by the reserved operation. Null only for a BLOCKED tombstone. |
| `applied_transaction_id` | VARCHAR(40), stored generated column `IF(state='APPLIED', transaction_id, NULL)`, UNIQUE | At most one effective deduction per transaction (FR-029) |
| `processed_at`, `restored_at` | TIMESTAMP(3); `restored_at` null unless RESTORED | |

The row is inserted after the stock rows are locked, in the same local transaction as any stock UPDATE. A duplicate request therefore serializes on those locks and then on the primary key (R8).

## Analytics schema (`cs6510_analytics`)

| Table | Columns | Rules |
|---|---|---|
| `accepted_scan` | `position` BIGINT PK, > 0; `source_transaction_id` VARCHAR(40); `source_scan_sequence` INT ≥ 1; `sku`; `received_at` | Unique key `(source_transaction_id, source_scan_sequence)` deduplicates redelivery (FR-042). `position` is assigned in the ingestion transaction and never changes (FR-043). Appends arrive in primary-key order. |
| `product_name` | `sku` (PK), `name`, `updated_at` | Upserted only when the in-memory name map lacks or differs from the name (R12) |
| `scan_sequence` | `sequence_key` (PK = 1), `last_position` ≥ 0 | The ingestion lock and position checkpoint. Equals the highest `accepted_scan.position`. |
| `popular_window` | `window_id` PK, `window_start`, `window_end` UNIQUE, `computed_at` | CHECK `window_end ≥ 1000`, `(window_end − 1000) mod 500 = 0`, and `window_start = window_end − 999` (FR-044) |
| `popular_item` | `window_id` FK, `rank_pos` 1–10, `sku` FK → `product_name`, `scan_count` > 0 | Primary key `(window_id, rank_pos)`; ordered by count descending, then SKU ascending (FR-045) |
| `analytics_checkpoint` | `checkpoint_key` (PK = 1), `last_window_end` | 0 or a valid boundary. It advances in the same transaction as the window header and ranks (FR-047). |

## In-memory projections (non-durable; R18, R19)

| Projection | Service | Contents | Source of truth | Updated | Rebuilt after restart |
|---|---|---|---|---|---|
| Product catalog snapshot | Transaction | SKU → name and price, immutable | `product_replica` | Atomic swap after a committed replica refresh | Loaded from `product_replica` at startup |
| Transaction state cache | Transaction | Per OPEN transaction: status, `item_count`, total, `attempt_count`, `active_attempt_number`, and lines (SKU → quantity, captured price, name). LRU cap set by `TRANSACTION_CACHE_MAX_ENTRIES`, default 100,000; 0 disables. Entries hold no lock: requests are serialized by `TransactionLocks`, 4,096 fixed lock stripes keyed by transaction ID. Stripes are never evicted, so eviction cannot create a second lock for one transaction (R19). | `transaction` + `accepted_scan` | Only after a successful commit, and only while holding the transaction's stripe. Invalidated before the stripe is released if the commit outcome is uncertain, so the next request reloads before any mutation. Evicted when COMPLETED. | Lazily, on first access: one transaction-row read plus one grouped read of `accepted_scan` |
| Settlement registry | Transaction | Transaction ID → future of the pending attempt's settlement | `transaction.active_attempt_number`, `checkout_attempt` | Completed under the stripe lock after the T3 or reopen commit | Empty. Waiters create futures as needed, check the database once per `CHECKOUT_WAIT_BACKSTOP_MS` and at the bound, and the recovery worker completes futures (R7). |
| Recovery schedule | Transaction | Due times of attempt keys to resume: handovers, reconcile entries, and backoff retries | PENDING `checkout_attempt` rows and their `next_retry_at` | When a request hands over or meets an ambiguous T1 commit, and when the worker reschedules | Rebuilt by the startup scan; a bounded safety scan every `CHECKOUT_RECOVERY_SCAN_SECONDS` adds anything missing (R7) |
| Catalog cache | Inventory | Catalog snapshot plus `catalog_version` | `catalog_item`, `catalog_meta` | Reloaded when `GetCatalogVersion` reads a new version | Loaded at startup |
| Product name map | Analytics | SKU → stored name | `product_name` | After a committed ingestion that wrote a name | Loaded at startup (at most 2,000 rows) |
| Window ring | Analytics | The last 1,000 SKUs by position. Frequencies are derived from the ring at each boundary, which needs no database read. | `accepted_scan` + `analytics_checkpoint` | For each consumed position | Prewarmed from the database at the checkpoint (existing `WindowFilter` behavior) |

Stock, attempt outcomes, operation records, events, positions, and published windows are never served from a cache when they decide an outcome.

**Ownership and scope**:
- Only the components in this table may hold mutable in-memory state such as maps: `ProductCatalogReplica`, `TransactionStateCache` (with `TransactionLocks`), `SettlementRegistry`, `RecoverySchedule`, `CatalogCache`, `ProductNameMap`, and the existing Analytics pipeline stages. Business services hold none, and an architecture test enforces this.
- Every projection is process-local. Correctness never depends on one, including when several Transaction instances work on the same transactions, because database guards and Inventory's idempotency decide every outcome (R7, R19).

## State machines

### Transaction and checkout attempt (Transaction Service)

```text
transaction: OPEN ──T1──▶ OPEN with active attempt n (attempt n PENDING; basket frozen)
                            │
                            ├─T3 (Inventory APPLIED)──────────────▶ COMPLETED   (attempt n COMPLETED)
                            └─reopen (Inventory definitive reject)─▶ OPEN        (attempt n REJECTED)
```

| Transition | Trigger | Guarded preconditions, in the `WHERE` clause | Effects, in one local transaction |
|---|---|---|---|
| Scan | Scan request | `status = OPEN`, `active_attempt_number IS NULL`, and `item_count` equal to the cached value | `item_count = cached + 1`; total increased by the line price; INSERT `accepted_scan` |
| T1 begin | Complete request; the cached `item_count` is at least 1 | `status = OPEN`, `active_attempt_number IS NULL`, and `item_count` and `attempt_count` equal to the cached values (`n` = cached `attempt_count` + 1) | `attempt_count = n`, `active_attempt_number = n`; INSERT the attempt with its `lines` snapshot and totals |
| T3 record completion | Inventory reports APPLIED, on the live request or by recovery | `active_attempt_number = n`; the attempt is PENDING | Transaction becomes COMPLETED with the supplied `completed_at` and the active attempt cleared; the attempt becomes COMPLETED with `settled_at` and `client_outcome` |
| Reopen | Inventory reports INSUFFICIENT_STOCK, INVALID_REQUEST, or STOCK_RESTORED | Same as T3 | Active attempt cleared; attempt becomes REJECTED with its reason |
| Stay pending | Timeout, lost reply, crash, `FAILED_PRECONDITION` | — | None, except `client_outcome = PENDING_ERROR` before a pending 500 and the recovery bookkeeping |

Lookup reads `status` from the database: OPEN until T3 commits (FR-035).

### Inventory checkout operation (Inventory Service)

```text
(absent) ──apply, all lines available──▶ APPLIED ──reserved restore──▶ RESTORED
(absent) ──apply, unknown or short SKU─▶ REJECTED
(absent) ──reserved restore────────────▶ BLOCKED (tombstone)
```

| Operation request | State before | Result |
|---|---|---|
| Apply | absent | APPLIED with stock deducted in one UPDATE, or REJECTED with nothing deducted |
| Apply | APPLIED or REJECTED | Recorded outcome, replayed; `FAILED_PRECONDITION` if `lines` differ |
| Apply | RESTORED or BLOCKED | `STOCK_RESTORED`, with no change |
| Restore | APPLIED | Lines added back; becomes RESTORED |
| Restore | RESTORED | Already restored |
| Restore | REJECTED or BLOCKED | Nothing to restore |
| Restore | absent | Inserts BLOCKED; nothing to restore |

### Accepted-scan event

```text
Transaction accepted_scan:  UNDELIVERED ──Analytics acknowledges──▶ DELIVERED (delivered_at set)
Analytics accepted_scan:    stored with its position, in one ingestion transaction ──pipeline──▶ counted in eligible windows
```

### Popular window

A window is either absent or published. Publication commits the header, all of its ranks, and the checkpoint together, in boundary order. Reprocessing a published boundary must reproduce identical ranks.

## Validation rules and their requirements

| Rule | Enforced by | Requirement |
|---|---|---|
| A Scan adds one unit at the line's captured price, with one accepted-scan row, in one local transaction | Guarded UPDATE + INSERT, then commit | FR-019, FR-040 |
| Scan precedence: 400, then unknown transaction (404), then not open (409), then unknown SKU (404); no product data gives 500 | Cache fast path; error responses confirmed against the database (R19) | FR-020, FR-023 |
| No unit joins a frozen basket | `active_attempt_number IS NULL` in every Scan guard | FR-035 |
| A stale cache never causes a lost update or a wrong outcome | Guarded writes, then re-evaluation from the database | FR-019, FR-029 |
| At most one pending and at most one completed attempt per transaction | Guarded T1 + unique generated columns | FR-029 |
| All-or-nothing stock effect; stock never negative; contention never reported as insufficient | Locking SELECT in SKU order, one CASE UPDATE, CHECK constraint, internal deadlock retry | FR-026 |
| At most one effective deduction per transaction | Unique `applied_transaction_id` | FR-029 |
| A repeated request returns the original outcome; a different payload is rejected | Primary key + canonical `lines` comparison | FR-028 |
| Events counted once; positions unique, gapless, and immutable | Unique source pair; positions assigned under the `scan_sequence` lock in the ingestion transaction | FR-042, FR-043 |
| Windows cover exactly 1,000 positions at a 500-position hop, with deterministic top-ten ranks | CHECK constraints + the existing Window and Ranking stages | FR-044, FR-045 |
| Settled reconciliation across services | `db/validate-invariants.ps1` (R13) | FR-038, SC-002 |

Operational status queries and the FR-054 counts are listed in [contracts/service-deployment.md](contracts/service-deployment.md#operational-status-fr-039).
